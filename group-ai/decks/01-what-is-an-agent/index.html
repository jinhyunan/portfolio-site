도구는 이미 있습니다. 그런데 다음에 뭘 할지는 매번 사람이 정합니다.
시킬 수는 있는데, 맡길 수가 없습니다.

다음 단계를 누가 정하는가

정해진 규칙대로 실행

if · else · 매크로 · 스크립트. 사람이 미리 적어둔 경우만 처리하고, 적어두지 않은 경우는 사람에게 온다.

다음 단계 · 사람

01

자동화

rule-based · deterministic

한 번 묻고 한 번 답

LLM이 답을 만든다. 그러나 파일을 열지도, DB를 조회하지도 않는다. 바깥 세계와 상호작용하지 않는다.

다음 단계 · 사람

02

챗봇

LLM · single turn

흐름 자체를 스스로 정함

도구를 쓰고, 결과를 보고, 다음을 다시 정한다. 목표만 주면 끝날 때까지 반복한다.

다음 단계 · Agent

03

Agent

LLM + tools + loop

Agent = 자동화의 손 + 챗봇의 머리 + 스스로 다음을 정하는 루프

04 / 13

그 머리는 무엇을 하는 기계인가

확률이 가장 높은 다음 말을 고를 뿐입니다.
이게 LLM의 전부입니다.

생각하지 않는다 · 검색하지 않는다 · 계산하지 않는다 — 이 단순한 기계로 어떻게 일을 맡기는지가 남은 내용

05 / 13

일하는 장면을 세 칸으로

손 칸에 들어가는 게 아까 그 자동화다 — 없어지는 게 아니라 Agent의 손발이 된다

06 / 13

자료 칸은 사실 세 칸입니다

세 번째 칸이 가장 자주 빠진다 — 없으면 매번 처음부터 다시 시작한다

07 / 13

빈칸을 다 채워도, 아직 맡길 수는 없습니다

칸을 채운 상태는 멈춰 있습니다.
이 되돌아오는 화살표가 있어야 비로소 맡길 수 있습니다.

08 / 13

그런데 이 루프는 저절로 돌지 않습니다

입력input
사양서 · 기준서요청사내 시스템 · DB운전 데이터
추론 · 계획확률적 · LLM
요청 분석계획 수립도구 선택Context 관리
실행결정적 · 코드
작업 실행오류 처리 · 재시도결과 검증승인 요청
출력output
검토 의견계산 결과시스템 반영기록 · 추적

판단은 확률적, 실행은 결정적.
이 둘을 섞지 않고 잇는 배선이 harness(하네스)입니다.

도구를 언제 쥐어줄지 · Context에 뭘 넣고 뺄지 · 절차를 어떤 그래프로 그릴지 · 언제 멈출지 — Claude Code·Codex가 잘한 건 모델이 아니라 이 설계

09 / 13

맡길 수 있는 크기로 쪼갭니다

업무 전체를 통째로 넘기는 게 아닙니다.
절차를 나누고, 나눈 조각마다 맡길지 말지를 정합니다.

  • 자료를 모으는 쪽, 초안을 쓰는 쪽, 그 초안을 뜯어보는 쪽.
    사람 팀을 짜는 것과 같습니다.
  • 단계 수와 Agent 수는 다릅니다. 하나가 여러 단계를 맡아도 됩니다.
    나누는 건 역할이 다를 때뿐입니다.
  • 가장 단순한 구성에서 시작하고, 필요할 때만 자율성을 늘립니다.

질문은 “AI가 내 업무를 다 할 수 있나”가 아니라 “내 업무의 어느 조각부터 맡길 수 있나”

10 / 13

사내에서 Agent를 개발한다는 것

새로운 게 아닙니다. 아까 그 세 칸을 우리 것으로 채우는 일입니다.

사내 LLM API

이미 쓸 수 있습니다. 다음 말을 고르는 머리.

머리

LLM

in-house API

Python · 사내 DB

이미 쓰고 있습니다. 파서, 조회, 계산 — 지금의 자동화가 그대로 손이 됩니다.

손

Tools

python · db · parsers

우리 자료

도면, 사양서, 그리고 엔지니어의 판단이 기록된 자료. 우리한테만 있는 것.

자료

Context

docs · history · SOP

세 칸 모두 지금 있는 것 — 남는 일은 harness를 짜는 것뿐이고, 그 작업을 코딩 Agent와 함께 한다

11 / 13

실제로 만들어본 것

기자재 입찰 기술평가 보조 도구. 세 칸이 이렇게 채워졌습니다.

01

손

parser

제출 엑셀을 파서로 읽어 항목 · 조건 · 이력으로 정규화

Python · openpyxl — 벤더마다 다른 시트 배치를 규칙으로 흡수. 여기까지가 자동화.

02

손

ML tool

ML 예측 모델 — 이 항목이 승인될 확률을 계산

우리 판정 이력으로 학습 — 상용 LLM이 모르는 우리 기준을 확률로 알려준다. 도메인 특화는 모델 교체가 아니라 도구로.

03

자료

RAG

과거 판정 이력에서 지금 항목과 비슷한 건을 찾아 붙인다

문서 검색(RAG) — 비슷한 문장을 찾아 판단 재료로 넣는다.

04

머리

LLM

판정 · 근거 · 응답 초안을 낸다

사내 LLM API — 확률과 유사 사례를 근거로 쓰고, 그 근거를 함께 출력하게 강제.

05

루프

missing

결과를 보고 스스로 다음을 정하는 부분

아직 없다 — 7장의 그 되돌아오는 화살표. 남은 건 harness고, 그래서 완성품이 아니라 출발점.

정답이 있는 계산은 LLM이 추정하지 않고 도구가 한다 · LLM은 어떤 도구를 언제 쓸지만 정한다

12 / 13

맡기더라도, 사람이 정하는 것

  • 무엇을 맡길지, 어디까지 맡길지 — 사람이 정합니다.
  • 무엇을 “끝났다”로 볼지, 어디서 멈춰 승인을 받을지 — 사람이 정합니다.

맡긴다는 건 손을 떼는 게 아닙니다.
어디까지 맡길지를 설계하는 일입니다.

13 / 13

세 줄 요약

  • Agent는 “목표 → 도구 → 관찰 → 다시 판단”을 반복하는 LLM 시스템입니다.
    시키는 게 아니라 맡기는 것입니다.
  • 판단은 모델이, 계산·조회는 도구가, 책임은 사람이 맡습니다.
    도메인 특화도 도구로 합니다.
  • 가장 단순한 구성에서 시작해 신뢰가 쌓인 만큼만 자율성을 넓힙니다.
