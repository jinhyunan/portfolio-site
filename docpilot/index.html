Full-stack Document AI · LangGraph Agent

An air-gapped document AI app,
evolved into a declarative agent

DocPilot is an offline-first full-stack desktop web app for engineering documents (specifications, contracts and technical reviews). Built with FastAPI + React, it ships as a single PyInstaller exe and calls LLMs through an OpenAI-compatible endpoint (OpenRouter by default). One principle — tools over tokens. Deterministic code handles calculations and validation; the LLM handles orchestration and narrative.

01

Context — abundant site documents, restricted networks

Specifications, contracts and technical-review documents on EPC and plant projects are voluminous and repetitive. Yet many sites prohibit external internet and cloud SaaS for security reasons. DocPilot addresses both constraints: (1) it chains four document stages (translate, analyze, review, write) in one app, and (2) installation and startup require only a single executable + local server to run in a browser on an air-gapped network. Swap the LLM gateway to use the same app with an internal endpoint or OpenRouter.

Stages light up sequentially when you scroll into this section. Translate operates independently of this pipeline, with column, whole-file and sentence modes.

  • Translate — Translate columns, entire files (preserving sheets and structure), or individual sentences; retry only failed rows.
  • Analyze — Sends each full row to the LLM as JSON. The prompt template uses {context}/{item_data} placeholders to inject domain context such as document type, contractor and owner.
  • Review — Paginate, search and filter analysis results, then export selected records to Excel/PDF.
  • Write — Generates a Deviation List (proposal, rationale and revised wording) in the role of “Lead Proposal Engineer,” chained directly from Analyze results.

Analyze's placeholder context system (top left), the Write and Review modules, and Settings consolidated around one OpenRouter key. Credentials are stored in a locally encrypted file.

04

tools over tokens — LLM orchestration, reliability in code

Industrial domains with little tolerance for errors cannot rely on an LLM alone. DocPilot funnels LLM calls through one thin client (llm_client.py), wrapped in a deterministic reliability layer.

Reliable calls

A global concurrency semaphore, exponential-backoff retries, 429/Retry-After handling and a typed error taxonomy (AUTH/RATE/TIMEOUT/TRUNCATED/…) turn failures into specific codes.

Run recovery

The batch runner manages progress and cancellation, restores active runs after a browser refresh, and retries only the rows that failed.

Any gateway that follows the OpenAI-compatible schema (/chat/completions, Bearer) works. Switching from the internal LLM gateway to OpenRouter required replacing just this client file.

05

Offline delivery — run an executable

build_windows.ps1 installs dependencies from an offline wheelhouse and uses PyInstaller onedir to build DocPilot.exe. Launching it starts a local FastAPI server at 127.0.0.1 and opens the default browser automatically. Secrets are encrypted with Fernet and stored locally; the app communicates externally only with the LLM endpoint. The Python runtime is included in one folder for transfer into an air-gapped environment, without Electron or Tauri.

06

Evolution — adding a declarative LangGraph agent

After stabilizing the app, I explored its evolution into an agent in a separate package (agents/). It performs deviation reviews of EPC specification clauses using a state machine whose complete workflow is declared in YAML and compiled with langgraph. The deployed app runs without langgraph; the agent is an isolated capability showcase.

Named routers return branch labels only; the final status is always written by a deterministic node. Ambiguity triggers a clarify loop (up to 2 attempts by default). If exhausted, the agent reports needs_human_review transparently, without manufacturing certainty.

The traces below are from actual OpenRouter smoke-test runs.

$ python -m agents.run --input samples/validation_fail.json · Clause citing GB/T 700 as its sole standard

  2. clarify(attempt=1):  confidence=0.90  ambiguous=False
  3. validate: ok=False  issues=["standard_ref body 'GB/T' is not a recognized standard"]
  4. output:  status=validation_failed

08

Why this project — limitations and next steps

  • Through actual deployment — A full-stack app built and deployed as a single exe for air-gapped environments, beyond a prototype.
  • tools over tokens — A reliability layer and deterministic gates that preserve verifiability in the LLM era.
  • Declarative orchestration — Workflows declared in YAML and compiled with langgraph, with ambiguity branches, self-correction and transparent flags.

Limitations: standard-reference validation for deviation reviews uses only an illustrative demo set (ASME/ASTM/API/ISO/EN/ANSI), and the agent has few samples. Next: connect a standards-reference database, extend workflows by document type, and revalidate with an internal gateway.
